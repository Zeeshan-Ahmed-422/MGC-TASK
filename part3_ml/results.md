# Part 3 - lead scoring baseline, results

Generated by `python part3_ml/train.py`.

## Cleaning decisions

- Loaded 9,160 rows, 20 columns from data/leads.csv.
- Date range: 2024-01-01 to 2025-10-01.
- Deduplicated on crm_record_hash with the Part 2 winner rule: 9,160 -> 9,000 rows (160 duplicate rows removed).
- Normalised city: 21 raw spellings -> 9 cities (same mapping as part2_sql/queries.sql).
- Target `converted`: 626 of 9,000 leads = 6.96% base rate.

## Columns dropped as leakage

Recorded only after a lead is worked, so unknowable at the moment we need a score:

- **`token_amount_received_pkr`** - Pure target leakage. Every one of the 634 converted leads in the raw file has a token > 0, and no lead with a token of 0 ever converted - paying a token IS booking. (719 leads have a token > 0, so 85 paid and were still not marked converted: bookings that fell through.) Either way the column is only known after the sale, so it cannot score a new lead.
- **`site_visits`** - Only known after the lead is worked. Conversion runs 4% at 0 visits to 67% at 4 visits, so it looks like a brilliant feature; a brand new lead always has 0.
- **`calls_made`** - Post-contact activity. A lead we have called six times is a lead we already decided to chase - the model would learn our own past prioritisation, not the buyer's intent.
- **`total_call_seconds`** - Post-contact activity, same reason as calls_made.
- **`whatsapp_replies`** - Post-contact engagement; zero for every lead at the moment we need to score it.
- **`first_response_minutes`** - How fast WE replied. Measured after the lead arrives, and it is an action we take, not an attribute of the lead. Including it would also mix up cause and effect: leads the team liked got called back faster.
- **`agent_experience_years`** - Attribute of the agent the lead was assigned to, not of the lead, and assignment happens after creation. Scoring an unassigned lead with it is impossible, and it would bake in which agents got the good leads.

## Columns dropped as identifiers

- **`lead_id`** - Identifier. Unique per row, so it carries no signal and would let a tree memorise individual leads.
- **`crm_record_hash`** - Identifier (the CRM's hash of the buyer's contact details). Used for deduplication, never as a feature.
- **`created_at`** - Used to ORDER the train/test split, and dropped as a feature. A raw timestamp only tells the model 'later rows look like this', which is exactly the pattern that will not hold for next month's leads.

## Other data-quality notes

- `area` is missing for 477 leads (5%). Kept, with the missing values encoded as their own 'missing' category rather than imputed - 'we never captured the area' is itself information about how the lead came in.
- `bedrooms` is missing for 3,602 leads (39%), and almost all of those are Plots, Commercial Shops and Farmhouses, which have no bedroom count. Missing here is structural, not a data-entry failure, so it is median-imputed and the property type carries the real signal.
- `budget_pkr_lac` is missing for 284 leads (3%); median-imputed.
- No column in this file is constant or free text, so there was nothing to drop on those grounds.

## Features used

- Categorical (one-hot): `source`, `city`, `area`, `property_type`
- Numeric (median-imputed): `budget_pkr_lac`, `bedrooms`, `is_overseas`, `referred_by_existing_client`, `has_financing_approved`

All of them are known the moment the lead lands in the CRM.

## Time-based split

Train: 7,200 leads, 2024-01-01 to 2025-05-27, 6.71% converted. Test: 1,800 leads, 2025-05-28 to 2025-10-01, 7.94% converted.

Sorted by `created_at`, oldest 80% to train, newest 20% to test. A random split would let the model learn from leads that arrived *after* the ones it is tested on, which overstates performance and hides drift. This split answers the question we actually have: trained on the past, does it rank next month's leads?

## Metric

**PR-AUC (average precision) is the headline number.** Only 7.9% of the test leads convert, and with imbalance like that ROC-AUC is dominated by how well the model orders the huge negative class - it looks respectable even when the top of the list is wrong. PR-AUC only cares about precision and recall on the positives, which is exactly what a call list is: a sales team works down from the top, so what matters is how many of the leads it flags are real. ROC-AUC is reported alongside because it is the number most people expect to see.

| Metric | Model | No-skill baseline |
|---|---|---|
| PR-AUC | **0.1914** | 0.0794 (the base rate: guessing at random) |
| ROC-AUC | **0.7133** | 0.5000 (a coin flip) |

PR-AUC is 2.4x the no-skill baseline.

## What it means for the sales team

The test set is the newest 1,800 leads, of which 7.94% converted.

- Call the **top 100** leads by score: **29 conversions**.
- Call **100 leads at random**: **7.9 conversions** expected (100 x the base rate).
- That is a **3.65x lift** - the same 100 calls produce roughly 3.7 times as many sales.

## Model comparison

| Model | PR-AUC | ROC-AUC | Top-100 conversions |
|---|---|---|---|
| LogisticRegression (baseline) | 0.1914 | 0.7133 | 29 |
| RandomForest (comparison) | 0.1767 | 0.6989 | 29 |

The submitted model is the logistic regression: it is the simpler of the two, it is a baseline as the brief asks, and picking whichever model won on a single test set is how you start overfitting that test set. No hyperparameter tuning was done at all.

## Honest limitations

- A ROC-AUC near 0.71 on intake-only features is a weak-but-real signal. It is enough to order a call list, which is all it is for; it is not enough to decide that a lead is hopeless.
- The model's useful signal is concentrated in a few features (referral, financing approved, source, property type). It would be worth checking that those flags are actually populated at intake in the live CRM and not backfilled later - if `has_financing_approved` is often set after the first call, it is leakage too and I would need the CRM's audit log to tell.
- No calibration. The probabilities are usable for ranking, which is the job; they should not be read as 'this lead has an 18% chance of buying' without a calibration curve.
